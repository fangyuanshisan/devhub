# 外部插件生态评估与预备设计

本文用于外部插件生态设计评估。当前 DevHub 项目目标已统一为 **Core + 插件 的开源服务底座**：Core 提供账号、权限、内容、后台、API、SEO、安全边界和插件生命周期等稳定基础能力，插件承载业务扩展、前后台入口、Hook、配置、内容类型和第三方集成等扩展能力。

当前有效插件架构和路线图以 `docs/PLUGIN_ARCHITECTURE.md` 与 `docs/PLUGIN_SYSTEM_ROADMAP.md` 为准。本文作为外部插件运行模型的预备设计补充，不代表已经支持插件市场、远程自动安装、动态加载或执行第三方代码。

## 外部插件形态评估

### 方案 A：源码级插件

插件代码随 DevHub 一起编译发布。

- 优点：安全边界清晰，部署简单，符合当前内置插件模式。
- 缺点：不支持在线安装，需要重新构建发布。
- 适用：官方内置插件和强治理场景。

### 方案 B：manifest + 配置型插件

插件只声明内容类型、权限、菜单、配置、Hook 元信息，不执行第三方代码。

- 优点：安全性较高，适合先做插件包校验、安装、配置、启停和审计。
- 缺点：业务能力受平台通用能力限制。
- 当前状态：已支持 manifest JSON 校验、dry-run、插件包治理、zip / staging 链路、安装 / 启用 / 升级治理与审计；第三方前端挂载、后端隔离运行、HTTP 插件服务协议和市场分发仍未完成。
- 推荐：作为外部插件第一阶段。

### 方案 C：外部服务型插件

插件作为独立服务运行，DevHub 通过 HTTP/Webhook 调用。

- 优点：隔离性好，适合复杂业务。
- 风险：需要签名、鉴权、超时、重试、熔断和审计。
- 当前状态：仍为设计和评估，不执行真实 Webhook 调用。
- 推荐：作为第二阶段评估。

### 方案 D：Go 动态插件

使用 Go plugin 或类似机制。

- 风险：跨平台、部署和安全复杂。
- 当前不推荐。

### 方案 E：脚本沙箱插件

使用 JS/WASM/Lua 等沙箱执行插件逻辑。

- 优点：灵活。
- 风险：需要资源限制、权限隔离和安全沙箱。
- 结论：后续再评估。

## 推荐路线

1. 第一阶段：manifest + 配置型插件。当前已成为插件包治理和生命周期治理的基础形态。
2. 第二阶段：插件运行模型设计。明确第三方插件的前端、后端、Hook、权限、配置、API 调用和安全隔离模型。
3. 第三阶段：外部服务型插件。后续需要补 HTTP 插件服务协议、签名、鉴权、超时、SSRF 防护、失败策略和审计。
4. 第四阶段：评估 iframe / sandbox / postMessage 等前端插件挂载方式。
5. 暂不推荐：Go 动态插件和脚本沙箱插件直接进入生产链路。

## 插件包格式

```text
plugin.zip
  manifest.json
  README.md
  assets/
  migrations/
  admin/
  frontend/
  docs/
```

## manifest 校验

安装前必须校验：

- `code` 唯一。
- `version` 合法。
- `compatible_core_version` 匹配。
- `permissions`、`content_types`、`config_schema`、`hooks`、`migrations` 合法。
- `dependencies` 满足版本约束。

## 安全设计

- 插件包签名。
- 插件来源和上传权限控制。
- 插件包大小限制。
- 文件类型白名单。
- 禁止危险可执行文件。
- 外部服务签名鉴权、超时和重试。
- 所有安装、升级、启停、配置、迁移、Hook 失败写审计。

## 依赖设计

- `depends_on`
- `optional_dependencies`
- `core_version`
- 插件版本范围
- `dependency_missing` 生命周期状态
- 依赖插件禁用 / 归档后的降级策略

## 升级设计

1. 上传新版本。
2. 校验兼容性。
3. 展示变更说明和影响范围。
4. 备份配置。
5. 执行迁移。
6. 更新版本。
7. 写入审计。

## 卸载设计

- 禁用：关闭新发布和入口。
- 归档 / 软卸载：保留配置、内容、迁移和审计，可恢复。
- 硬卸载：高风险能力，后续阶段再设计，不作为当前目标。

硬卸载必须明确是否删除配置、内容、表、迁移记录和审计。
