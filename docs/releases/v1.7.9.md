# v1.7.9：Webhook non_blocking 链路总验收与 blocking Hook 设计评估版

更新时间：2026-05-18

本轮定位：对 v1.7.4 ~ v1.7.8 已落地的 Webhook **non_blocking** 链路做总体验收收口，并补齐 blocking Hook 的风险评估与后续拆分建议。

> 重要边界：本轮不实现 blocking Hook，不执行第三方插件代码，不做动态加载，不做插件市场，不做 OAuth/SSO，不新增复杂消息队列系统。

## 1. non_blocking 链路总体验收结论（概览）

已具备闭环（以“治理可追踪 + 失败不阻断主流程”为目标）：

- Events：`webhook_events` 持久化 + Admin 列表接口 + 后台 Events Tab
- Deliveries：`webhook_deliveries` 持久化 + 手动重试 + retry-due 扫描
- Retry：`retry_scheduled/retry_exhausted`、`next_retry_at`、`attempt/max_attempts`
- Circuit breaker：`closed/open/half_open` + `next_probe_at` + 手动恢复
- Signing：DevHub 发送端 HMAC-SHA256 签名（headers 完整；落库脱敏）
- Secrets：create/rotate/disable/enable/revoke + active/previous grace window（明文只展示一次）
- Callback token：create/rotate/disable/enable/revoke + scopes + community_scope（明文只展示一次，仅保存 token_hash）
- Callback API：`config.read` / `audit.write` 最小回调通道 + request 记录 + 审计

仍需保持口径（未做）：

- blocking Hook 未实现（仅做设计评估）
- 第三方插件运行时（真正的 http_service 自动投递、插件 marketplace、动态加载、第三方代码执行）未实现

## 2. blocking Hook 设计评估结论（摘要）

结论：**blocking Hook 可以进入“设计收口阶段”，但不建议直接进入实现阶段**。外部 HTTP blocking Hook 会影响主流程可用性与延迟，需要满足最小前置条件后再进入实现。

建议策略：

1. blocking Hook 默认关闭，且需要管理员显式开启（按 hook 级别、插件级别、社区级别三者至少其一）。
2. 仅允许极少数 `before_*` hook 进入 blocking 白名单；第三方插件默认推荐 non_blocking。
3. 默认超时 2s（最大 5s），并明确超时后的“拒绝/放行/降级”策略（按 hook 类型细分）。
4. blocking Hook 禁止后台自动重试；失败需强审计与可观测性（避免重复用户动作）。
5. 外部 HTTP blocking Hook 若开放第三方插件使用，必须引入更强的信任模型（trusted publisher / official）与熔断降级策略。

详细风险与拆分建议见：`docs/PLUGIN_WEBHOOK_PROTOCOL.md` 与 `docs/PLUGIN_WEBHOOK_IMPLEMENTATION_PLAN.md`（v1.7.9 补充）。
