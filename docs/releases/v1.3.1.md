# DevHub v1.3.1 - 插件化关键入口封口与权限校验补强版

[返回文档入口](../README.md)

发布日期：2026-05-10

## 版本定位

DevHub v1.3.1 是 v1.3.0 Core + Plugins 架构后的技术债收口版本。本版本不新增插件、不实现插件市场、不实现动态插件加载，重点封住旧写入口，补强后台内容创建和更新时的插件权限边界，并进一步规范插件平台契约与运行时治理。

完整插件系统是当前最高优先级长期主线。本版本处于 P0 插件平台收口阶段；插件包、插件市场、远程安装、在线更新和动态加载进入 P2 / P3 路线，但不属于 v1.3.1 已实现能力。

## 本版本已完成

- `Service.CreatePost` 已封口，不再作为常规业务写入口，也不再直接调用仓储裸写入。
- `/api/v1/posts` 写接口继续废弃，`POST/PUT/DELETE /api/v1/posts*` 返回 `410 Gone`，读取兼容仍保留。
- `repo.CreatePost` 仍保留为 legacy / seed / migration / 兼容层内部能力，不作为业务创建入口。
- `POST /api/v1/admin/posts` 在基础 `post.create` 兼容权限之外，叠加真实内容类型对应的插件 create 权限。
- 后台创建内容内部仍转到 `Service.CreateTopic`，继续执行全局插件状态、子站插件状态、板块绑定、`allowed_content_types` 和权限码校验。
- 后台编辑内容采用稳妥策略：禁止修改子站、板块、`content_type` 和 `plugin_code` 等归属字段。
- 后台内容编辑 UI 在编辑态禁用子站和板块选择，避免误导管理员以为普通编辑可迁移内容归属。
- MemoryStore / MySQLStore 的站点管理员角色补齐插件 create 权限，避免后台兼容创建入口因新增动态权限而误伤演示管理员。
- `PluginManifest` / `ContentTypeDefinition` / `PermissionDefinition` / `MenuDefinition` / `RouteDefinition` / `HookDefinition` 契约已补齐自动化结构测试。
- `CreateTopicRequest` 的 `ActorPermissions` 和 `ActorContext` 均由服务端从 token、后台身份和版主 scope 计算，客户端请求体不能覆盖。
- `plugins.config_json` 已落库并提供 `PUT /api/v1/admin/plugins/:code/config`；`community_plugins.config_json` 继续作为子站配置层。
- 插件配置合并规则更新为：默认配置 / `config_schema` < `plugins.config_json` < `community_plugins.config_json`，API 返回 `resolved_config.default/global/community/effective`。
- Service 层已有最小内部 HookBus，当前调用点覆盖 `BeforeCreateContent`、`AfterCreateContent`、`BeforeUpdateContent`、`AfterUpdateContent`、`BeforeDeleteContent`、`AfterDeleteContent`、`AfterCreateComment`、`OnSearchIndex`、`OnNotificationBuild` 和 `OnSEOBuild`。
- 插件治理审计新增 `admin_logs.old_value`、`admin_logs.new_value` 和 `admin_logs.metadata_json` 结构化字段；全局插件状态、全局配置、子站插件状态、子站配置和子站排序会同时保留 `target` 摘要与结构化 diff。
- 新装 schema 与启动迁移辅助已包含结构化审计字段；老库升级可执行 `db/mysql/migrations/007_admin_logs_structured_plugin_audit.sql`。
- 公共插件接口会隐藏 `config_json` 和 `resolved_config`，避免把后台配置暴露给前台。
- 后台插件页“进入管理”改为读取 manifest 中的 admin 菜单路径，不再在页面内硬编码 qa/docs/wiki/projects/jobs/ai_works 路由。

## 权限规则

后台 `admin/posts` 创建入口当前采用“双层权限”：

- 第一层：`post.create`，作为历史后台内容创建兼容权限。
- 第二层：按归一后的 `content_type` 和 `plugin_code` 动态校验插件 create 权限。

动态 create 权限：

- `question -> qa.question.create`
- `document -> docs.document.create`
- `wiki_page -> wiki.page.create`
- `project -> projects.project.create`
- `job -> jobs.job.create`
- `ai_work -> ai_works.work.create`
- `article/news -> core.topic.create`，并兼容旧 `post.create`

`post.create` 是过渡兼容权限，不是长期主权限。后续需要随着 Core 内容定义收口或 article/news 插件化逐步降低它的业务含义。

## 后台更新策略

后台普通编辑当前只允许修改非归属字段：

- 标题
- 摘要
- 正文
- 标签
- 状态
- 置顶
- 精华

后台普通编辑禁止修改：

- 子站 / `community_id`
- 板块 / `category_id`
- `content_type`
- `plugin_code`

如后续需要跨子站、跨板块或跨插件迁移内容，应新增迁移专项接口，并逐条校验目标子站、目标板块、全局插件状态、子站插件状态、`allowed_content_types`、当前用户权限和插件扩展表一致性。

## 当前限制

- HookBus 仍是最小内部调度器；Search / Notification / SEO 目前只有事件派发，尚未实现复杂插件处理器、统一错误日志和重试策略。
- `plugins.config_json` 与 `community_plugins.config_json` 当前只校验 JSON 格式，暂未做 `config_schema` 强校验。
- 非插件历史审计日志可能仍只有 `target` 文本摘要，尚未全部迁移为结构化 diff。
- Store 层仍可保留 `content_type` / `plugin_code` 防御性归一，但业务校验必须在 Service / Router 层完成。
- `topics` / `categories` 仍是真实表名，`contents` / `channels` 是目标概念命名。
- `project` / `job` / `ai_work` 已插件归属，但专属业务表和完整业务闭环仍待后续版本。

## 插件平台路线

- P0：Manifest、Registry、ActorContext、权限码、两层插件状态、板块绑定、发布校验、菜单过滤、config_json、config_schema 基础校验、HookBus、结构化审计、migration 边界和测试矩阵。
- P1：schema 自动表单、插件 SDK 文档、插件生成模板、依赖检查、版本兼容检查、插件事件 / 通知模板、搜索索引和 SEO 扩展。
- P2：本地插件包、插件安装、插件升级、soft uninstall、插件 migration runner、插件包签名校验和插件市场雏形。
- P3：远程插件市场、在线更新、动态加载能力评估、插件沙箱和插件权限隔离。

## 验收清单

- `Service.CreatePost` 不再能绕过插件校验。
- `/api/v1/posts` 写接口返回 `410 Gone` 或明确废弃。
- `POST /api/v1/admin/posts` 创建 `question` 需要 `qa.question.create`。
- `POST /api/v1/admin/posts` 创建 `document` 需要 `docs.document.create`。
- `POST /api/v1/admin/posts` 创建 `wiki_page` 需要 `wiki.page.create`。
- 缺少对应插件权限时返回 `403`。
- 禁用 `qa/docs/wiki` 后，后台兼容创建入口不能创建对应内容类型。
- 后台普通编辑不能修改子站、板块、`content_type` 或 `plugin_code`。
- 已有内容列表、详情、评论、标签、收藏和关注不受影响。
- `/topics/:id` SEO 动态 HTML 和 `/c/:slug` SEO 不受影响。
